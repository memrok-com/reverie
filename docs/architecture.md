# Architecture

Pi owns source conversations, active branches, model/provider settings, credentials and the terminal. The extension owns character/folder associations, persona editing, controls, source projection and process supervision. The Rust engine owns memory, chronology, reflection validation and retrieval.

## Local package

`@memrok-com/reverie-pi` declares one Pi extension entry. Its bundled JavaScript uses Node built-ins. Native binaries live under `bin/<platform>-<arch>/`. The verified release currently includes Windows x64 only. Unsupported platforms fail with an explicit compatibility message rather than downloading code.

The extension starts a native process lazily for each character in use and speaks a JSON-lines stdio protocol. The process asks the adapter for source or reflection. Reflection uses Pi's configured model registry, preserving request-time authentication. The child environment excludes credential-shaped variables. Local retrieval does not invoke a model.

Reflection callbacks use a configurable inactivity deadline (ten minutes by default), renewed by text/thinking deltas through a callback-scoped `callProgress` message. Progress for an expired or unrelated callback cannot renew another operation; source reads retain their separate absolute three-minute deadline. Timeout aborts the host callback and fails publication atomically. Transport timeout settings are excluded from reflection input fingerprints so tuning them cannot regenerate memory. `REVERIE_REFLECTION_INACTIVITY_SECONDS` configures new extension processes; native clients can set `reflectionInactivityMs` in engine settings.

## Durable state

A WAL-mode SQLite catalog stores characters and personas, canonical folder associations, folder-specific model choices, source session paths and selected leaves, reply recall explanations, shortcut preferences and deletion tombstones. The native SQLite database stores scoped episodes, selective recollections and derived impressions. Both live under Pi's agent data directory, outside the installed package.

Pi normally waits for a user/assistant message before writing a session file. On quit or session replacement, Reverie writes a dated, unplayed session's header and metadata to its Pi session path and registers it as a source. It never does this during reload, when the same session manager will continue and still owns its first flush. No dialogue is fabricated. Episode chat controls can recover legacy date-only records into a fresh Pi runtime with their original identity or explicitly delete them even when no source path was registered.

Folder links are opt-in. Unlinked Pi use remains ordinary coding-agent use. Linked character chats suppress coding tools and use the character foundation. A session's original character identity is recorded in both Pi metadata and the catalog; relinking cannot transfer an existing chat's memories.

Explicit model selections and thinking-level changes update a folder's saved provider, model and thinking level. The catalog migrates older model preferences with an initially unset thinking level, then captures the current effective level on first restoration. Restoration sets the model before applying thinking through Pi's capability clamping, even when the model already matches. Restoration never changes Pi's global defaults or saves a fallback as the new preference. Input and reroll guards restore the saved choice before generation; a context guard also aborts continuation paths on a model mismatch. Memory reflection passes the captured thinking level to the model as well. Missing models or credentials pause generation until the user selects an available replacement. Credentials remain in Pi's own configuration.

At request time, the system-context hook supplies the persona and, only when recall is nonempty, a clearly labeled private memory section. Recollections are fallible background data rather than dialogue or instructions. Empty recall contributes no placeholder. No user or assistant turn is fabricated, and the player's latest message remains the final dialogue turn. This projection is not saved as played source; legacy custom recall messages are filtered out before model conversion. Pi's normal custom-message path is avoided because it converts custom entries to user messages.

The same single system projection can include a separate bounded historical section. The adapter reads successful reply records from the selected branch, checks character/episode ownership and a played-prefix fingerprint, and supplies references rather than old prose as evidence. Native validation resolves them against currently eligible contribution state hashes and recollection indices. It retains at most eight distinct recollections within a 6,000 UTF-16 code-unit JSON budget, selecting four recent references and then emotionally salient remainder, with first/latest associations. Historical sections are never expanded recursively. Source callbacks attach these associations separately from dialogue; reflection validates them against staged earlier contributions, uses short current-message/episode aliases, and includes nonempty validated history in reuse fingerprints. Raw association fingerprints are rechecked before publication. Empty history preserves existing input fingerprints; this feature does not globally resample episodes or disturb correction prefixes. See [recall history](recall-history.md).

## Source and alternatives

Player inspection uses a separate native `inspect` operation over complete published contributions, with no cue, ranking limit or model call. The adapter displays stored recollections, impression snapshots and chronological eligibility separately from saved reply-context explanations. Played excerpts are transient source callbacks; inspection never enters dialogue, model context or compaction. Source unavailability preserves the last published contribution while exposing an explicit freshness warning.

The native schema migrates version 1 to version 2 by adding character-scoped correction snapshots. A reviewed correction pins an episode's recollections against its source and preceding-memory fingerprints. Preview/application uses a per-process token, database revision and fresh source check; application atomically replaces the recollections, clears current impressions and invalidates later derivatives. Generated impression rebuilding receives the reviewed recollections. Earlier-source deletion or correction releases dependent snapshots; other source/prefix changes block reuse until explicit release. See the [inspection and correction contract](memory-inspection.md).

Source follows Pi entry identities and parent links through the chosen branch. It includes played user/assistant text and the foundation recorded for that episode, excluding tool results, custom UI entries, injected recall and compaction summaries. Original played entries remain available through compaction. Source hashes detect meaningful changes before native publication.

Reroll navigates to the preceding user message and resubmits it. Alternative cycling navigates to an existing reply and appends a state-only selection anchor, making selection survive restart. No rejected-branch summary is carried into the story. Re-memorization replaces the episode's previous contribution and refreshes dependent later reflections.

Changing provider, model or thinking level does not invalidate published memory. Contributions retain their original model route as `modelKey` provenance and their original `inputHash`; a separate `reuseHash` validates reflection version, source, interval, label, preceding memory and settings independently of the route. Changed inputs still refresh the affected contribution and dependent later reflections with the requested model. The ordinary Pi rebuild explicitly sends `force: false` and repairs changed inputs only.

Pi exposes deliberate full regeneration separately as **Regenerate with current model** (`/reverie regenerate`). It captures the restored folder provider/model/thinking route and uses native inspection to count included episodes and identify corrections in canonical order. A scrollable preview explains scope, new model calls/costs, possible changes to recollections and impressions, and correction protections. Corrected included episodes after the first included episode are listed with labels, dates and direct inspection commands. Pi refuses to confirm or start regeneration until those corrections are explicitly released, avoiding paid earlier reflections that cannot publish if a later correction's pinned prefix changes. The first included episode has an empty prefix, so its reviewed recollections can be preserved; excluded episodes and their corrections are ignored by this preflight. No corrections are released automatically.

When preflight passes, a separate compact interactive confirmation repeats the character, route, count and cost/change warning. With no included episodes it reports that memorization is needed. Cancellation before confirmation sends no rebuild. After confirmation it rechecks the active session, character binding, enabled/idle state and inspection's memory revision before requesting native `rebuild` with `force: true` and the captured `modelKey`. Source is read from selected Pi branches; excluded episodes stay excluded.

Full regeneration uses the existing native staging/publication transaction, source/revision validation and cancellation path. A model failure, cancellation during work, or changed correction dependency discards the staged contributions and leaves the last published state intact; already incurred provider usage remains. Reviewed recollections are supplied as authoritative model context and preserved exactly by the engine, while impressions may be resampled. Native correction dependency guards remain in place for direct clients and concurrent changes. Pi explains how to inspect and explicitly release a blocking correction through its separate preview/confirmation workflow. Reflection context limits and model-dependent output quality apply to regeneration as to ordinary formation.

Legacy contributions lack independent validation and model provenance. When their old input fingerprint matches the currently requested route, they acquire validation metadata without model calls or changes to their published state/dependency identities. If the route already changed before this adoption, the engine conservatively refreshes them rather than assuming their old settings and reflection version match. A later reviewed correction can still require release in that legacy case. Reuse metadata and model provenance are excluded from published state hashing, so metadata adoption preserves correction prefixes.

## Episode chronology

Pi's grouped **Episodes & dates** controls reuse complete memory inspection and canonical native episode order. Relative input resolves once from a chosen episode boundary; duplicate labels require explicit selection. Pi reads session entries (in memory for the active episode, from its saved source otherwise) and finds each branch tip's last effective time by following parent links. Shared prefixes are cached so every entry is visited once; superseded setup dates do not extend the interval. Effective times are translated using their recorded offsets, and the furthest tip or selected story point is supplied as `branchEnd` to native `previewRedate`. The engine validates the translated full extent while preserving the selected branch's end, records a process-local token and character revision, and lists affected contributions, released corrections and eligible preceding episodes. Pi shows selected and full intervals separately and rechecks branch extent before applying. Unavailable saved sources block re-dating; legacy date-only setups have no branches to scan. Direct native clients without a branch extent retain selected-interval validation and must supply `branchEnd` when they own alternate branches. `applyRedate` checks that revision under an immediate transaction before shifting dates and invalidating derivatives. The cutoff is the earliest current, published or proposed start; invalidation covers published and current chronology. Inclusion choices survive for an explicit rebuild. No model call is required to move dates.

Before preview and application, Pi also resolves the actual selected leaf's effective date (the active manager leaf or the catalog's saved source leaf) and compares it with the native episode's selected time. A mismatch blocks re-dating with guidance to select a valid branch. This covers interior superseded setup entries whose date restoration previously failed, without counting all abandoned setup dates as branch extents or altering tree navigation itself.

For an already saved session, changing its story date immediately updates the catalog's selected leaf after appending the time entry. Another window can then re-date that episode without waiting for a reply or clean shutdown. Date-only sessions without a source file retain Pi's deferred save behavior; no transcript is forced into existence.

Native schema version 3 adds a zero-default `time_offset` to episodes, preserving version-1/2 contributions during migration. The cumulative shift translates Pi's existing branch time entries without rewriting files or changing entry IDs/selected leaves. New time entries record their current offset; branch restoration subtracts that recorded offset before adding the episode's current shift. Input and continuation refresh native chronology so another window's date shift is observed before retrieval. Future inspection stays in transient player UI. Dialogue and saved reply explanations retain their original wording; native contribution validation prevents obsolete memory references from becoming current context. Backups preserve offsets and import older archives with a zero offset.

## Deletion

Returned impressions carry their snapshot owner's episode ID separately from supporting episode citations. Deletion matches both: an impression can be authored by a withdrawn episode while citing only earlier episodes, without any of its author's individual memories being retrieved. The owner is resolved from the canonical contribution at retrieval, so old published contributions need no regeneration. Saved legacy impressions without an owner have irrecoverable provenance; deletion conservatively clears their prose and rendered `text` copy for the same character, including when an unmemorized draft is deleted. Surviving records retain unrelated structured recollections, historical context and played-prefix evidence, preserving earlier reflection inputs and activations. Explain last recall identifies the missing legacy impression context. The same redaction protects late legacy writes after a deletion tombstone; a process-local `discardedRecallCount` exposes rejected saves that explicitly reference a known deletion.

Known source files are checked on startup, periodically and before recall. A missing file creates a durable tombstone only if its parent directory remains accessible. Missing directories and disconnected drives remain unavailable sources until they return, or the player explicitly deletes the episode. Unreadable sources retain their saved memory and produce one warning per unavailable period, while other sources continue reconciling. Readability recovery permits a new warning on a later failure; failed notifications are retried. Memory operations that need an unavailable source report its read error without publishing partial results. Cleanup is idempotent. Native `forget` removes unmemorized source without invalidating unrelated memory. For published source it invalidates derivatives from the earlier of the current and published start, consistently using published episode identities for memories, contributions and pins. Surviving inclusion choices remain intact. A revision increment prevents in-flight reflection from republishing deleted source. A model-backed rebuild restores affected memory from surviving source.

Recall cleanup combines episode scope with reply-level provenance. Before native deletion, the catalog saves a durable plan using the earlier of the target's current and published starts. For published targets it includes same-character episodes at or after that boundary in either chronology, including ongoing episodes. Regardless of publication, it also finds individual same-character replies naming the target through fresh/historical memories, impression sources or shared-history sources. Withdrawn or previously invalidated memory is therefore removed from explanations and backup without erasing unrelated replies, even after re-dating. A genuinely unmemorized draft has no referencing dependents. Native deletion checks the character revision captured with the plan. Cleanup and tombstone acknowledgment are atomic and idempotent; old episode-only plans remain supported, and both scopes survive interruption after native deletion removes its dates. Acknowledgment rechecks references, while transactional reply saving rejects context referencing a known deletion or belonging to a deleted source. Original transcripts are deleted only by an explicit delete action or the host/user; the memory engine does not delete source files. Built-in Pi deletion has no extension event in 1.3.0, so reconciliation is required in addition to Reverie's integrated delete command.

Retrieval identifies a candidate by its stored per-episode row ordinal, using an indexed query and the canonical published memory vector. Candidate queries and contribution resolution share a SQLite read snapshot, so another process cannot swap their versions between reads. Matching prose and floating-point scores are not identity checks. Backup exports order memory rows by their original IDs; restore validates those IDs and sorts by them before allocating new rows, preserving episode ordinals even if the archive array was reordered. Reflection history exposes only short episode/recollection and current-message aliases plus the relevant content, scores and activation times; contribution hashes, native indices, detail-supply flags and raw background message IDs stay outside model input. Nonempty-history input version 2 tracks this projection change; episodes with no history retain their existing input contract.

## Story portability

Versioned story ZIPs contain one character's scoped catalog/native snapshot and canonical Pi sources with selected leaves. Backup captures and verifies metadata under short write locks, with source I/O outside them; changes to the story abort capture. Restore validates a separate native database before publication. A journal and process-lifetime SQLite ownership lock recover interrupted imports without relying on PID liveness. Restored Pi sessions remain canonical under the destination data directory, with relocated headers and no dependency on old paths. Account credentials and unrelated stories are excluded. See the [backup contract](story-backup.md).

## Boundaries

The previous Node engine and DSH adapter are retired. Their user data is neither erased nor automatically imported. Pi does not provide a complete built-in persona or reply-variant product: those controls belong to this extension. Episodic reflection still needs the full selected source to fit the chosen model's context window. Dates are explicit Gregorian dates/zoned timestamps; episodes cannot interleave.
